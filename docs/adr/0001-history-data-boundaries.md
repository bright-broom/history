# ADR-0001: 注入可能なストレージ境界と厳格な YAML 読み込み

**Status:** Accepted
**Date:** 2026-09-11
**Deciders:** この変更で採用。リポジトリのメンテナーがレビュー。

## Context

15年・34件の月別イベントを持つ、読み取り中心の小規模 Next.js アプリ。
既存の層分けではサービスが infrastructure のシングルトンを直接生成していた。
スキーマ検証失敗後も元データを読み込み、読み込み障害は null / 空配列になり、
誤ったデータの静的生成を検出できなかった。独自の変換処理では sources 配列を文字列として判定して失っていた。
また、全リポジトリが同じキャッシュキーを共有し、別データルートの値が混入した。

## Decision

Next.js と Git 管理の YAML を維持し、アプリ内の境界を強制する。

1. ドメインに `IHistoryRepository` を置き、サービスのコンストラクタに必須で注入する。
2. `src/server/history.ts` だけでデフォルトサービスとファイル実装を接続する。
3. ファイル読み込み → YAML 解析 → Zod 検証 → パスとの一致確認 → ドメイン変換の順に処理する。
4. 文書欠落のみ null とする。データルート欠落と I/O 失敗は DataLoadError、解析／検証失敗は DataParseError。
5. リポジトリごとにキャッシュを持ち、同じキーの並行読み込みをまとめる。失敗は保存せず、戻り値を複製する。
6. 依存方向を ESLint、サーバー境界を server-only、動作をテストと全カタログ検証で守る。
7. npm に依存管理を統一し、CI でロックファイルから再現・検証する。
8. 監査で検出された既知の脆弱性に対応し、Next.js / eslint-config-next を16.3.4へ更新。その他は npm audit fix で互換範囲内の修正版を適用する。

## Options Considered

| 選択肢 | 複雑性・運用コスト | 拡張性 | 評価 |
|---|---|---|---|
| 既存のグローバル関数と寛容な読み込みを維持 | 低い | 保存先変更・障害診断が困難 | 不採用 |
| 同一アプリ内のポートと注入 | 小さい。新サービスの運用不要 | 保存先の差し替えと単体検証が可能 | 採用 |
| DB/API・外部キャッシュを別サービスとして導入 | 高い。移行・認証・バックアップが必要 | 大規模更新と横断検索に適する | 現時点では不採用 |

## Trade-off Analysis

厳格な検証はデータが一部壊れていても表示を続ける可用性と引き換えに、
誤った静的ページを公開することを防ぐ。Git で編集し CI で検出できる本アプリに適する。
メモリキャッシュの値を複製するため CPU／メモリの追加コストがあるが、共有値の改変を防げる。
TTL は10分、最大512件。複数プロセス間の共有・無効化は行わない。
未知の追加 YAML フィールドは Zod の標準動作で除去し、既知のフィールドを検証する。

## Consequences

- UI を変えず、出典が正しく復元される。無効なURL数値や存在しない暦日を拒否する。
- YAML の不整合はビルド／リクエストの失敗として表面化する。404として隠さない。
- サービスを利用する新コードはストレージを注入するか、サーバーのファサードを利用する。
- テスト用の可変シングルトンリセットを廃止し、テストごとに独立したリポジトリを作る。
- 静的生成内容の変更には再ビルド・再デプロイが必要。
- 件数は月別イベントの合計。年の主要イベントとの重複集計をしない。
- DB 移行は、編集API・検索・更新頻度・データ量が要求する時点で再検討する。
- 検証は歴史的事実そのものの正しさを保証しない。
